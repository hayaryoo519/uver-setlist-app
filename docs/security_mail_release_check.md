# 認証メールのリリース確認

この手順は登録、認証メール再送、パスワード再設定、メールアドレス変更のリリース条件です。APIの受付成功、SMTP認証成功、受信箱への配送成功は別々に確認します。

## 設定と非送信チェック（担当エンジニア）

1. Staging専用の送信アカウント、受信できるテストアドレス2つ（同じ担当者が受信する別名でも可）、専用HTTPSのStaging URLを用意します。本番のメール秘密値をStagingへコピーしません。
2. Stagingサーバーのチェックアウトにある `.env` を既存の所有者・600権限を維持してエディタで編集します。設定するのは `EMAIL_SERVICE`、`EMAIL_USER`、`EMAIL_PASS`、`APP_URL`。秘密値をシェル引数・履歴・チャット・Issue・スクリーンショットへ出しません。DB/JWT/OAuth等の設定は変更しません。
3. `APP_URL` は専用StagingのHTTPSオリジン（例: `https://staging.example.invalid`）です。パス・クエリ・フラグメント・URL内の認証情報を付けません。本番モードはlocalhost/ループバックやHTTP、URL未設定を拒否します。
4. 担当エンジニアがuploadsを退避してから設定を反映し、コンテナ起動、退避画像の復元・照合、Stagingと本番のping、変更対象外の環境ファイルの一致を確認します。設定だけ変えた場合もコンテナの再作成が必要です。再作成でuploadsが失われる現状があるため、退避前に再作成しません。
5. 実行中のコンテナ設定を、値を表示せず確認します。

   ```sh
   docker compose exec -T app-staging node server/scripts/check_email_configuration.js
   docker compose exec -T app-staging node server/scripts/check_email_configuration.js --smtp
   ```

   1つ目は設定の検証だけです。2つ目はSMTPへ1回接続して認証しますがメールは送りません。失敗時は終了コード1と固定文言だけを返します。失敗を成功扱いにせず、設定を修正してから再確認します。SMTP認証の大量再試行はしません。
6. 成功結果にも `inbox_delivery_verified: false` が出ます。SMTP接続確認だけでは送信者受け入れや受信箱到着は証明できません（[Nodemailer公式](https://nodemailer.com/smtp#verifying-the-configuration)）。続く受信確認が必要です。

## 受信者に依頼する確認

受信者が必要なのはメールの到着・差出人・リンク先の確認とリンクを開く操作です。設定・サーバー点検・架空データでの異常系検証は担当エンジニアが行います。Staging専用設定の確認前には実施しません。

| 確認 | 操作 | 合格条件 |
| --- | --- | --- |
| 登録と認証 | StagingでテストアドレスAを登録し、届いた認証リンクを開く | 専用差出人、HTTPSのStagingリンク。認証後にログインできる。メールの期限表示は24時間 |
| 再送 | 未認証のテストアドレスBについて、発行から1分以上待ってログイン画面の再送導線から依頼 | 最新メールが届き、最新リンクで認証できる。前のリンクは失敗する。パスワードは変更されない |
| 再設定 | Aで再設定を依頼し、届いたリンクで新パスワードを設定 | 期限表示は1時間。旧パスワードと旧セッションは拒否され、新パスワードでログインできる |
| メール変更 | Aの設定画面で空いている変更先アドレスを入力し、現在のパスワードを入力して保存。変更先のメールを開く | 確認前は旧アドレスを維持し、確認後だけ変更。確認後は旧セッションを拒否し新アドレスでログインできる。期限表示は1時間 |
| 未着・期限切れ | 迷惑メールフォルダも確認。再送導線、メール変更の再依頼を確認 | 受付を配送完了と誤表示せず、再依頼できる。実際に期限を待つ試験は担当者と調整し、実DBの期限を直接書き換えない |

アドレスBが既に登録されている場合はメール変更先に使えません。メール変更用は空いているテスト用の別名Cを使うか、再送確認を後に行います。既存アカウントの削除やメール移動で空きを作る操作はしません。

結果として伝えるのは「項目・日時・合否・表示された固定エラー」です。メール内のURL、認証トークン、SMTP秘密値、パスワード、メール本文のスクリーンショットは送らないでください。テスト用アカウントの後片付けは担当者と対象を確認して行います。

## リリース判定

- [ ] 設定検証とSMTP認証の終了コードが0。
- [ ] 上記の受信・確認・再設定・変更を実施し、担当者と日時を記録。
- [ ] 期限切れ・削除済み・同時使用・旧セッション・変更先競合・回数制限を隔離DBで確認。
- [ ] ログにメール・リンク・SMTPエラー詳細がないことを確認。
- [ ] 本番でも専用の設定検証・SMTP認証を行う（本番DBを直接操作しない）。Stagingの成功で本番の配送を検証済みにしない。

本番モードとNODE_ENV未設定/未知の値では設定不足を送信スキップにしません。APIは登録有無を隠す受付応答を維持し、配送失敗は固定ログに記録します。アプリのping成功はメール準備完了を意味しません。明示した `NODE_ENV=development` / `test` での未設定スキップと、永続配送キュー・自動再送が未実装である制約は残ります。
