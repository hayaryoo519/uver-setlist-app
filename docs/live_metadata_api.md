## スキーマ

新規 `server/migrations/033_live_metadata.sql`、`034_live_artists.sql` を通常のマイグレーション手順で適用する。
使い捨てPostgreSQLへの適用/再適用・制約・同時更新は検証済み。既存のStaging/本番DBへの適用は未実施。

- `live_metadata`: 公演ごとの自動候補 `candidates` と手動設定 `overrides` を分離し、`revision` を持つ。
- `live_metadata_history`: 管理者・操作種別・変更前後・日時を同一トランザクションで記録する。
- 既存のライブ/セトリのカラムやデータは変更しない。旧コードの公演編集・CSV更新はこれらのテーブルを更新しない。
- 公演削除では関連情報・履歴を削除する。ユーザー削除では履歴の管理者IDをnullにする。
- 既存公演の属性行は初回更新時に作成する。未作成の場合は候補/手動設定とも空、revision 0。

## 管理者専用API

すべて既存の `authorize` / `adminCheck` を適用する。候補原文・管理メモ・手動設定を公開APIには返さない。

### GET /api/lives/:id/metadata

取得内容：`live_id`, `candidates`, `overrides`, `revision`, `effective`, `artists`（確認済み共演者が参照する辞書）。
公演が存在しなければ404。不正な公演IDは400。

### PATCH /api/lives/:id/metadata/candidates

```json
{
  "revision": 0,
  "patch": {
    "tags": ["vs"],
    "countryCode": "KR",
    "sourceId": "fixture-id",
    "sourceUrl": "https://example.test/live",
    "ruleVersion": 1,
    "original": { "info": "UVERworld vs Fixture Artist" }
  }
}
```

候補の対応フィールド：`tags`, `countryCode`, `memberIds`, `sourceId`, `sourceUrl`, `ruleVersion`, `original`。
項目省略はその取得元の既存候補を保持する。タグ/メンバー候補のクリアは空配列、国・出典のクリアはnullを明示する。
`sourceId` 指定時はその取得元の候補を更新し、省略時は現在の主取得元を更新する。クリアしても別取得元に候補が残る場合は集約結果に残る。全取得元を覆す訂正には手動設定を使う。
原文はオブジェクトを保存する。候補入力全体は64KBまで。保存する原文に認証情報や不要な個人情報を含めない。
URLはhttp/httpsのみ受け付け、取得アクセスは行わない。
候補更新は手動設定に触れない。

取得画面の `metadataCandidates.status` は画面内の未確認表示であり、このAPIでは受け付けない。
検索画面の新規追加では、下記の `metadata_source` を公演追加APIへ送信する。

### PATCH /api/lives/:id/metadata

```json
{
  "revision": 1,
  "patch": {
    "tagOverrides": { "add": ["birthday"], "remove": ["mens"] },
    "country": { "code": "KR" },
    "members": { "ids": ["takuya"] },
    "classification": { "needsReview": false, "note": null }
  }
}
```

- 項目省略：その項目の手動設定を保持する。
- 項目にnull：その項目の手動設定を解除し、自動候補へ戻す。
- `tagOverrides` はadd/removeの一組を置換する。同じタグの両方指定は拒否する。
- `members: { "ids": [] }` は「対象なしと確認済み」。`members: null` は未確認に戻す。
- `participants: { "items": [{ "artistId": 10, "role": "guest" }] }` は共演者を確認済みにする。items=[]は共演者なし、nullは未確認に戻す。ID・役割・関連保存は[共演者仕様](./live_collaborators.md)を参照。
- 開催国は有効なISO国コードを必須とする。「国なしで確認済み」は受け付けない。
- `classification` は分類検討の管理情報。自由な公開タグは生成しない。

タグID：`mens`, `womens`, `birthday`, `christmas`, `anniversary`, `vs`。
メンバーID：`takuya`, `katsuya`, `akira`, `nobuto`, `shintaro`, `seika`。
アコースティックとフェスはこの新しい保存APIの編集タグには含めない。
海外属性 `overseas` は手動タグとして入力せず、確認済み開催国がJP以外の場合に導出する。
確定済み対象メンバーは生誕祭の根拠として扱い、候補から生誕祭が消えても有効タグは保持する。
対象メンバーを確定したまま生誕祭を明示的に除外する矛盾は400で拒否する。
確認済み対バン相手はvsを導出する。vsの明示的な除外との矛盾も400。ゲスト/サポートだけでvsを生成しない。

## 有効情報

- タグ：自動候補に手動追加/除外を適用し、固定順で返す。
- 国：手動確定した国のみ公開用の有効情報にする。国候補だけでは海外タグを生成しない。
- メンバー：手動確定した対象のみ有効情報にする。空値と未確認を区別する。
- 共演者：手動確定したID・役割のみ。公開応答では正式名・別名も返す。確認済みなしと未確認を区別する。
- 候補のタグと、構造化情報の管理者確認は異なる扱い。

公開一覧/詳細は共通サービスで有効情報だけを投影し、tagsと公開metadataを返す。フロントはその値を優先し、空タグをテキスト再判定で復活させない。
公開タグのフェス重複は廃止し、既存ライブ種別で検索する。海外属性・確認済み国・対象メンバーでの検索を接続済み。

## 管理一覧のレビュー判定

`GET /api/lives/metadata-review` は管理者専用。公演ごとの適用項目の未確認、取得元不一致、分類検討を一括で返す。
公開APIにレビュー情報を追加しない。原文・候補値・管理メモ・履歴・管理者IDも返さない。
判定条件、通知リンク、未取得/失敗時の扱いは[レビュー導線](./live_metadata_review_queue.md)を参照。

## 競合・失敗時

- 更新にはGETで得たrevisionを必須とする。
- 公演行をロックして属性の初回作成と更新を直列化する。
- revision不一致は409。再読込して確認し、古い入力を自動再送しない。
- 保存と履歴を同じDB接続・同じトランザクションで処理する。
- 保存失敗・整合性エラー・履歴保存失敗はロールバックする。
- 更新処理は既存ライブの名称・特記事項やセトリを変更しない。

## 自動取り込みへの接続

共通サービス `server/services/liveMetadataCandidates.js` を追加。
判定語とルール版は `server/utils/liveTagRules.json` をフロントとサーバーで共用する。
アコースティックは辞書とUIから除去済み。フェスは既存種別に使用する判定語で、候補保存の編集タグには含めない。

### 検索画面の単件/選択一括追加

`POST /api/lives` に任意の `metadata_source: { type: "setlistfm", original: ... }` を追加した。
取得時のID・日付・ツアー名・説明・会場名・国コード・URLのみ送信し、曲一覧・投稿者情報は含めない。
候補タグをクライアントから確定値として受け取らず、サーバーで原文から生成する。

公演・setlist.fm ID・候補・変更履歴を同じトランザクションで保存する。
候補/履歴保存に失敗した場合は公演追加も取り消し、通知しない。
取得元IDと追加日付の一致を検証する。既存setlist.fm IDの重複は409。
原文なしの旧クライアントによる追加は従来どおりで、候補の自動生成は行わない。
楽曲/セトリ登録は従来の別要求であり、公演と候補の保存後の部分失敗は引き続き別対応が必要。

### 年代一括収集

新規公演では公演・セトリ・原文候補・履歴を同じトランザクションで保存する。
登録済みsetlist.fm IDでは公演名やセトリを変えず、原文候補のみ再取得する。
手動設定は更新しない。同一候補の再取得ではrevisionと履歴を増やさない。
ジョブの `totalSkipped` は公演作成をスキップした件数であり、候補更新がなかったという意味ではない。

### 公式スケジュール/ニュース取り込み

新規公演では公演追加・解析済み名称/出典の候補・変更履歴を同一トランザクションで保存する。
既存公演でも一覧から得た名称・出典の候補を更新し、既存の出典/時刻の関連付けを同じトランザクションに含める。
登録済みスケジュールの詳細ページは従来どおり再取得しない。最新の詳細本文の更新まで確認したという意味ではない。
ニュースの解析済み名称からVS等のタグ候補を生成するが、共演者のIDは自動確定しない。
国は会場名・タイムゾーンから推測せず、取得できない場合はnullを保存する。
候補保存失敗時は公演追加/関連付けもロールバックする。dryRunでは属性保存・トランザクション・通知を行わない。
既存の種別推測・時刻/タイムゾーンの関連付け方針は変更していない。

### 原文と情報源

サーバーでは公演原文の必要項目を平坦な `original` オブジェクトに保存する。
公式の原文はHTML全文ではなくパーサーが抽出した名称・日付・カテゴリ・出典・会場情報。
会場国コードの元表記も保持し、検索候補用の国コードは大文字へ正規化する。

`candidates.sources` に取得元IDごとの最新スナップショットを保持する（公式スケジュールID、公式ニュースID、setlist.fm ID）。
上位の `tags` 等は集約結果。取得元IDごとの変更前の値は履歴に保持する。

集約方針：
- タグ/対象メンバー候補：各取得元の和集合。名前から確定情報に昇格させない。
- 国候補：値のある公式情報を優先し、公式が不明ならsetlist.fmで補完する。
- 原文/主出典：公式、setlist.fm、旧候補の順。同順位は取得元IDの辞書順で決め、取得順に依存させない。
- 国候補の不一致：`conflicts` に候補値を残す。優先値を選んでも管理者確認済みにはしない。
- 手動追加/除外・国・メンバー：集約後に適用し、取得元追加/更新で変更しない。
- 同じ候補の再取得はrevision/履歴を増やさない。

従来の単一候補は次の候補更新時に取得元別スナップショットへ移し、失わず保持する。
新しいマイグレーションは不要で、033のJSONB構造の中で保持する。
1公演16取得元・取得元データ合計256KBまで。超過は保存失敗として扱い、黙って原文を削らない。
同一企画の古い取得元にタグが残っている場合は和集合にも残るため、管理者の手動除外で訂正する。
取得元同士のタグ不一致を自動で真偽判定する仕組みではない。

**共演者を含む新機能の運用前に033/034マイグレーションが必要。既存のStaging/本番DBへの適用は未実施。**
