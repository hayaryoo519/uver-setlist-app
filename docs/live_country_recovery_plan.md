## 実ブラウザで確認した問題

2026-10-17、ユーザーが開いているStagingを閲覧・絞り込み操作で確認。
公開APIの642公演のうち過去626公演は、全件 `country.status=unreviewed` / `code=null` だった。
日本・海外の確認済みはどちらも0件。生誕祭を外して海外単独、日本単独でも0件になることを確認した。
この時点の公開API調査だけでは候補・原文の有無は判断できず、実DBや管理用候補を読んだ結果ではなかった。
実環境の保存・再取得・確定・同期は行っていない。

Windows標準OpenSSHの既存認証エージェントを使用し、新規の資格情報作成・鍵のコピー・SSH設定の変更はしていない。
コンテナのStagingサービスラベル・稼働状態を確認し、接続DB名もSQL側で制限。

## コード上の経路

| 経路 | 現在の扱い |
|---|---|
| `033_live_metadata.sql` | テーブル作成のみ。過去公演の国を埋める処理はない。適用済みSQLを編集して解決しない |
| setlist.fm単件/年別取り込み | `venue.city.country.code` を `buildSetlistCandidates` で候補化。`saveMetadataCandidates` が候補/出典を保存し、手動確定を変更しない |
| 公式取り込み | `buildOfficialCandidates` は国候補をnullにする。会場名やタイムゾーンからは国を推測しない |
| 有効値・公開API | `effectiveMetadata` は `overrides.country.code` のみを確認済みとする。候補があっても公開国/海外タグにはならない |
| 再取り込み | 候補の更新であって、国を確定する操作ではない |
| DB同期 | `anonymize.sql` は未確認の国候補・原文・出典等を除去し、公開用の確定国だけを維持する。同期を使った場合、Stagingに候補がない可能性がある |

したがって「もう一度全件取り込む」「国不明を日本扱いする」「候補を公開へそのまま出す」では解決しない。
候補が存在しないことと、存在するが未確認であることを分けて調べる必要がある。
同期で非公開候補を持ち出さない方針は、この対応で緩めない。

## 読み取り専用の診断SQL

`scripts/audit/live-country-coverage.sql` を用意し、承認後に上記のStaging集計だけを実行済み。本番では未実行。

- `BEGIN READ ONLY` / `ROLLBACK`、15秒のstatement timeout、固定search_path。
- 接続DB名が `uver_setlist_staging` または専用fixture名以外なら拒否。
- DB名だけでは接続先の安全性を保証しない。ホスト・ポート・対象環境・権限を確認してから実行する。
- 過去 / 当日以降 / 日付なしで分け、件数のみを返す。
- 公演ID・国候補の値・出典ID/URL・原文・管理メモ・資格情報は返さない。
- 集計区分：形式上の確定値あり / 手動設定の要確認 / 単一国候補 / 候補の不一致 / 候補の形式不正 / 候補なし。
- 候補なしについてsetlist.fm IDの有無も集計する。外部source IDは単なるハッシュの場合があり、あるだけで再取得可能とは判断しない。
- 既存metadata行がない公演、取得元別countryCode、不一致フラグも考慮する。
- **件数は補完の承認ではない。** 英字2桁の形式集計なので、ISO辞書・出典の正しさを保証しない。単一候補でも適用前に既存の国バリデーションと出典確認が必要。

## 元データの追加集計

`scripts/audit/live-country-source-coverage.sql` で以下のJSONだけを対象に、国情報の回収余地を件数で調べる。

- `live_metadata.candidates.original`
- `live_metadata.candidates.sources.*.original`
- `lives.import_metadata`
- `raw_setlists.parsed_json`（公演未関連の下書きも別区分）

再帰的な `countryCode` / `country.code` キーの存在と、値が英字2桁の形式かを調べる。
原文やコード値は出力しない。自由記述・`raw_text`・管理メモ・会場名・タイムゾーンは検索しない。
キーがあってもnull/不正形式ならコードありに数えない。英字2桁でもISO辞書・出典の正しさは保証しない。
同じ公演の複数下書きは文書件数と公演件数を分ける。未解析下書きは別件数にして、JSONがないだけで原文もないと誤認しない。
この追加SQLもREAD ONLY/ROLLBACK・DB名制限・timeoutを持ち、既存SQLと同じ接続条件/承認範囲で使う。

## 残る638公演の補完方針（未実施）

1. 既存の手動確定国は上書きしない。
2. 単一候補は、明示的な出典・ISOコード・公演との対応を確認し、管理者が承認した分だけ確定する。
3. 複数候補・不正な候補・壊れた手動設定は自動確定しない。
4. 候補なしでsetlist.fm IDがある場合、件数/レート制限/公演IDと日付一致を確認して再取得する別工程を検討する。勝手にジョブを起動しない。
5. 国だけの補完で曲・公演名・他の属性・共演者を変更しない。
6. 候補も照合できる出典もなければ未確認のまま残す。会場名・時期・タイムゾーンから日本を推測しない。
7. 適用はrevision照合・監査履歴・操作者を保持する既存の管理PATCHを基礎にする。一括SQLでoverridesを丸ごと置換しない。
8. まず少数の公演をイベント固有の公式日付・会場・所在地と一件ずつ照合し、照合不能・同日複数公演・表記差のあるものを保留する。年別件数や会場名から一括確定しない。
9. 部分的な整備状況で検索結果を完全な国内/海外件数と誤解させない表示も、別途検討する。

## 使い捨てDBでの検証

全schemaモードの `server/scripts/test-live-metadata-db.js` に診断SQLの検証を追加した。
所有data_directoryとloopback/非アプリポートを確認したクラスタ内だけに、独立したfixture DBを作る。
16件の合成公演で分類・出力の最小化・前後データ一致・対象外DB名の拒否を検証し、DBを削除する。
追加集計はネストした国情報・null/不正形式・不正sources型・複数/未関連/未解析下書き・自由記述から推測しないことも検証する。
通常モードの旧schema7項目はそのまま、全schema/実認証モードには診断の2項目を追加する。
実環境に接続せずにSQLの動作を再現できるが、実環境の候補件数を確定するものではない。
