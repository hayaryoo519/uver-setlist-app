状態：辞書API、共演者の保存/管理編集、公開表示/検索を実装。
使い捨てPostgreSQL 18で旧番号030/031のSQL内容・FK/検索/同時更新/再取得/同期匿名化を検証済み。未配備のため033/034へ改番（[DB検証](./live_metadata_db_verification.md)）。辞書登録/名称修正/別名検索は合成APIでPC/モバイルの[実ブラウザ検証](./live_metadata_browser_verification.md)も完了。実Stagingへの適用と実環境の結合確認は未実施。
取得テキストから共演者を自動確定・自動登録する処理はない。

## 分類と表記ゆれ

アーティストの正式名・別名は同じ固定IDに持たせる。
タグを「アーティストA対バン」のように増やさない。
公演との関連はアーティストIDと役割の組で保持する。

| 役割ID | 表示名 |
|---|---|
| co_headliner | 対バン相手 |
| guest | ゲスト |
| supporting_act | オープニング・サポート |

同一公演・同一アーティスト・同一役割の重複は拒否する。同じアーティストの異なる役割は許可する。
フェスの全出演者を対バン相手としない。EVENT種別だけで対バンとみなさない。

正式名の検索キーはNFKC・小文字化・前後/連続空白の整理をする。記号は削除しない。
同じキーの正式名は辞書へ重複登録できない。
別名は管理者が明示的に登録し、同一アーティスト内の正規化重複を除く。
別名が他のアーティストと一致しても自動統合しない。検索結果を確認して正しいIDを選択する。

## 保存構造

`server/migrations/034_live_artists.sql` を追加（033に続けて通常手順で適用する）。

- live_artists：正式名、検索キー、別名と別名検索キー、revision。
- live_collaborators：公演/アーティスト/役割の関連。FKで未登録IDを防ぐ。
- live_artist_history：辞書の登録/修正前後、管理者、日時。
- live_metadata.overrides.participants：公演単位の手動確認状態と関連リスト。

participants設定と関連テーブルは追加情報APIの同一トランザクションで更新する。
公演削除では関連行を削除し、関連があるアーティストはFKで削除を禁止する。辞書削除APIは設けない。
旧コードの公演編集・CSV・候補再取得は共演者の手動設定や関連行を変更しない。

## 管理用辞書API

すべて既存の認証/管理者チェックを適用する。

- GET /api/live-artists?search=...：正式名・別名の部分検索。最大100件。ワイルドカードはリテラルとして扱う。
- POST /api/live-artists：`{ name, aliases: [] }`。201で辞書レコードを返す。正規化正式名の重複は409。
- PATCH /api/live-artists/:id：`{ name, aliases: [], revision }`。同じIDの名称/別名を更新。競合は409。

辞書レコードは `{ id, name, aliases, revision }`。
名称/各別名は200文字まで、別名は30件まで。更新と辞書履歴は同一トランザクション。
別名変更だけでアーティストのIDは変わらない。

## 公演追加情報API

PATCH /api/lives/:id/metadata のpatchにparticipantsを追加。

```json
{
  "revision": 3,
  "patch": {
    "participants": {
      "items": [
        { "artistId": 10, "role": "co_headliner" },
        { "artistId": 11, "role": "guest" }
      ]
    }
  }
}
```

- participants項目省略：既存設定を保持。
- participants: null：未確認へ戻し、関連行を解除する。辞書のアーティスト自体は削除しない。
- participants: { items: [] }：「共演者なしと確認済み」。
- itemsに値：確認済みのID・役割リストとして保存。最大30件。
- 未登録ID、不正役割、同一ID/役割の重複は拒否。
- 確認済みの対バン相手があればvsタグを導出する。vsの手動除外との矛盾は拒否。
- ゲスト/サポートだけではvsタグを生成しない（名称等から別途候補がある場合は、その候補の判断は独立）。

管理用GET/更新応答には `effective.participants` と、使用中IDの辞書情報 `artists` を返す。
候補再取得はparticipantsに触れない。関連保存が失敗したら属性/履歴とともにロールバックする。

## 管理画面

公演一覧「属性」→「共演者の確認状態」で確認済みモードを選ぶ。

1. 名前/別名でアーティスト辞書を検索してIDを選択。
2. 対バン相手/ゲスト/オープニング・サポートを選び「共演者を追加」。
3. 既存関連の役割変更・削除が可能。
4. 「追加情報を保存」で公演との関連を確定する。

辞書にない場合は正式名と別名を登録する。既存辞書の名称/別名の修正もできる。
**辞書の登録・修正は即時保存。公演への関連付けは別保存。**
辞書を保存しただけでは公演へ自動追加しない。公演モーダルを閉じても辞書変更は取り消されない旨を表示する。
辞書の重複/競合では入力を保持し、再検索して既存レコードを確認する。
辞書処理中は公演側の保存/閉じる等を禁止する。
辞書変更後は公開一覧/全詳細キャッシュを無効化する（同じアーティストを別公演でも参照するため）。

## 公開APIと表示・検索

公開一覧/詳細のmetadataにparticipantsを追加。

```json
{
  "participants": {
    "status": "confirmed",
    "items": [{ "artistId": 10, "name": "Fixture Artist", "aliases": ["FA"], "role": "guest" }]
  }
}
```

未確認ではstatus=unreviewed/items=[]、確認済みなしではstatus=confirmed/items=[]。
確認済みの関連だけを表示し、辞書の正式名・公開別名・役割を返す。
辞書のrevision/検索キー/変更履歴/管理情報は公開しない。
一覧の辞書情報は全公演で必要なIDをまとめて1回で取得する。

一覧/詳細に役割と正式名を表示する。
公開一覧では共演アーティストID・役割による絞り込みと、正式名/別名の文字検索を行える。
アーティストと役割を両方指定すると、同じ関連項目に両方一致する公演だけを返す。
「アーティストAが対バン、アーティストBがゲスト」の公演を「Aがゲスト」で返さない。
これらは取得済み一覧のクライアント検索で、URL/APIクエリによる属性検索はまだ実装しない。
