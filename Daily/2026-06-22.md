**現在の流れ**
[deploy-production.yml](/home/haya-ryoo/dev/uver-setlist-app/.github/workflows/deploy-production.yml:10) は次の順番です。

1. 稼働中のディレクトリを `git reset --hard origin/main`
2. `npm install`
3. DBマイグレーション
4. フロントエンドを同じ場所でビルド
5. `systemctl restart uver-setlist`

Node プロセス自体は手順 5 まで動き続けます。ただし、いくつか注意点があります。

**実際に停止する場面**
- `systemctl restart` の瞬間は数秒程度 API が停止します。
- [uver-setlist.service](/home/haya-ryoo/dev/uver-setlist-app/server/uver-setlist.service:10) は起動前に `fuser -k 8000/tcp` を実行するため、旧プロセスを明示的に終了します。
- 新プロセスの起動に失敗した場合、`RestartSec=5` により 5 秒間隔で再試行します。その間は利用できません。

**マイグレーション中のリスク**
[migrate.js](/home/haya-ryoo/dev/uver-setlist-app/server/scripts/migrate.js:96) は SQL ファイルごとにトランザクションを張っているため、失敗時の壊れ方は抑えられています。

ただし、旧バージョンのアプリが稼働したまま DB を更新します。そのため以下の変更は危険です。

- 使用中カラムの削除・名称変更
- 大きなテーブルへの重い `ALTER TABLE`
- 長時間ロックを取るインデックス作成
- 新コードへの切替前に旧コードと互換性がなくなる変更

カラム追加や新規テーブル追加であれば、通常は問題になりません。

**おすすめの判断**
一人開発でアクセス規模がまだ大きくないなら、すぐに本格的な無停止デプロイを作る必要はありません。ただし Production には、デプロイ中だけメンテナンス画面へ切り替える仕組みを入れる価値があります。

最低限、次の運用ルールも決めておくと堅実です。

- マイグレーションは原則として後方互換にする。
- カラム削除は「新コードで未使用化」→ 次回リリースで削除、の2段階にする。
- リリース前に `npm run migrate:dry` を実行する。
- デプロイ後は指示書どおり `systemctl status uver-setlist` で起動時刻を確認する。

なお、Actions が途中で失敗した場合も要注意です。再起動前なら旧 Node プロセスは動き続けますが、ディスク上のコードや `dist` は更新途中です。将来的には「別ディレクトリでビルドして、最後に切り替える」方式へ変えると、この曖昧な状態も解消できます。

# Production デプロイ・DB変更ルール

## 1. 基本方針

- 本番反映は `main` へのマージだけでは行わない。
- 動作確認後に GitHub Release を publish し、Production Actions を実行する。
- 本番DBを手作業で直接変更しない。
- DB変更は必ず `server/migrations/` に SQL を追加する。
- 適用済みマイグレーションファイルは編集しない。修正は新しい SQL ファイルで行う。

## 2. マイグレーション命名規則

連番で追加する。

```text
025_add_xxx.sql
026_create_xxx.sql
```

番号の再利用や過去ファイルへの追記は禁止する。

## 3. 通常リリースで許可するDB変更

原則として、旧バージョンと新バージョンの両方が動く変更だけを許可する。

許可例:

- nullable なカラム追加
- デフォルト値付きカラム追加
- 新規テーブル追加
- 新規インデックス追加
- 既存データを壊さないデータ補正

注意が必要な例:

- `NOT NULL` カラム追加
- 大量レコードの一括更新
- 大きなテーブルへのインデックス追加
- 外部キー追加

これらはデータ量とロック時間を確認してから実施する。

## 4. 1回のリリースで禁止する変更

以下は必ず複数回のリリースに分ける。

- 使用中カラムの削除
- カラム名変更
- 型の破壊的変更
- 既存値の意味を変える変更
- 旧コードが読めなくなる制約追加

例: `old_name` を `new_name` に変更する場合。

1. `new_name` を追加する。
2. 一時的に両方へ書き込む。
3. データを移行する。
4. 読み取りを `new_name` に切り替える。
5. 次回以降のリリースで `old_name` を削除する。

## 5. リリース前チェック

Release publish 前に、最低限以下を確認する。

```bash
npm test
npm run build
cd server
npm test
npm run migrate:dry
```

加えて確認する内容:

- マイグレーションが後方互換か
- `.env` の追加・変更が必要か
- バックアップが必要な変更か
- 数分以上かかる処理が含まれていないか
- メンテナンス画面を出す必要があるか

## 6. メンテナンス画面を出す条件

次の場合は、事前にメンテナンスモードへ切り替える。

- カラム削除や名称変更を含む
- DBロックが長くなる可能性がある
- 大量データ更新を行う
- デプロイ中に旧コードとの互換性を維持できない
- 復旧に手作業が必要になる可能性がある

通常の nullable カラム追加や小規模な新規テーブル追加では不要とする。

## 7. デプロイ後チェック

Actions 成功後、Production サーバーで確認する。

```bash
sudo systemctl status uver-setlist
journalctl -u uver-setlist -n 100 --no-pager
```

ブラウザでも最低限確認する。

- トップページが表示できる
- ログインできる
- ライブ一覧・ライブ詳細が開ける
- 変更した機能が動く
- API に `500` が出ていない

## 8. 失敗時の対応

- Actions が失敗したら、原因確認前に Release を再実行しない。
- DB変更を手作業で巻き戻さない。
- 追加型のマイグレーションであれば、原則として DB はそのまま残し、アプリだけ前バージョンへ戻す。
- データ破損や個人情報への影響が疑われる場合は、先にサービスを停止する。
- 復旧後に原因と対応を記録する。

## 9. 将来改善

利用者や更新頻度が増えたら、次を検討する。

- Production のメンテナンス画面
- デプロイ前の自動バックアップ
- 別ディレクトリでビルドしてから切り替える方式
- ヘルスチェック成功後に旧プロセスを停止する方式
- Actions 内での自動スモークテスト

最初にドキュメント化するなら、[docs/development_workflow.md](/home/haya-ryoo/dev/uver-setlist-app/docs/development_workflow.md) に概要、[docs/db_operations.md](/home/haya-ryoo/dev/uver-setlist-app/docs/db_operations.md) にDB固有ルールを置く構成が読みやすいです。


```text

```

```bash
import type { QueryResult, QueryResultRow } from "pg";

export type Queryable = {
  query<T extends QueryResultRow>(text: string, values?: unknown[]): Promise<QueryResult<T>>;
};

// 通知の種類。月末精算リマインドを起点に、要確認通知などへ拡張していく。
export type NotificationType = "settlement_reminder" | "review_reminder";

// 配信チャネル。まずはアプリ内記録(in_app)のみ。PWA push は後続で push を足す。
export type NotificationChannel = "in_app" | "push";

export type NotificationStatus = "pending" | "sent" | "failed" | "read";

export type EnqueueNotificationInput = {
  householdId: string;
  recipientMemberId: string;
  type: NotificationType;
  title: string;
  body: string;
  channel?: NotificationChannel;
  // 同一通知の二重配信を防ぐ冪等キー(例: `settlement:2026-06`)。
  // 省略時は都度配信(重複チェックなし)になる。
  dedupeKey?: string | null;
};

export type ReviewReminderResult = {
  candidates: number;
  created: number;
};

const enqueueQuery = `
  insert into notifications (household_id, recipient_member_id, type, channel, title, body, dedupe_key)
  values ($1, $2, $3, $4, $5, $6, $7)
  on conflict (household_id, recipient_member_id, type, dedupe_key) where dedupe_key is not null
  do nothing
  returning id::text
`;

const markSentQuery = `
  update notifications
  set status = 'sent', sent_at = now()
  where id = $1 and status = 'pending'
  returning id::text
`;

const markReadQuery = `
  update notifications
  set status = 'read', read_at = now()
  where id = $1 and status <> 'read'
  returning id::text
`;

const reviewReminderCandidatesQuery = `
  with review_counts as (
    select household_id, count(*)::int as review_count
    from expenses
    where scope = 'review'
    group by household_id
  )
  select
    hm.household_id::text,
    hm.id::text as recipient_member_id,
    hm.review_reminder_frequency,
    rc.review_count
  from household_members hm
  join review_counts rc on rc.household_id = hm.household_id
  join households h on h.id = hm.household_id
  where h.status = 'active'
    and hm.review_reminder_frequency <> 'off'
  order by hm.household_id, hm.created_at asc
`;

function formatDateKey(date: Date) {
  const year = date.getFullYear();
  const month = String(date.getMonth() + 1).padStart(2, "0");
  const day = String(date.getDate()).padStart(2, "0");
  return `${year}-${month}-${day}`;
}

function isMonthEndReminderWindow(date: Date) {
  const lastDay = new Date(date.getFullYear(), date.getMonth() + 1, 0).getDate();
  return lastDay - date.getDate() <= 5;
}

// 通知配信の入口。記録を1件作成する。
// dedupeKey が指定され、同一の通知が既に存在する場合は作成せず null を返す(冪等)。
export async function enqueueNotification(queryable: Queryable, input: EnqueueNotificationInput): Promise<{ id: string } | null> {
  const result = await queryable.query<{ id: string }>(enqueueQuery, [
    input.householdId,
    input.recipientMemberId,
    input.type,
    input.channel ?? "in_app",
    input.title,
    input.body,
    input.dedupeKey ?? null,
  ]);

  const row = result.rows[0];
  return row ? { id: row.id } : null;
}

// 配信完了として記録する(pending のもののみ)。実際の push 送信はこの呼び出しの後段で足す。
export async function markNotificationSent(queryable: Queryable, id: string): Promise<boolean> {
  const result = await queryable.query<{ id: string }>(markSentQuery, [id]);
  return result.rows.length > 0;
}

// 受信者が既読化したときに記録する。
export async function markNotificationRead(queryable: Queryable, id: string): Promise<boolean> {
  const result = await queryable.query<{ id: string }>(markReadQuery, [id]);
  return result.rows.length > 0;
}

// 要確認支出が残っている世帯メンバーへ、設定頻度に応じたアプリ内リマインドを作成する。
// dedupeKey は日単位にして、同じ日に再実行しても二重作成しない。
export async function enqueueReviewExpenseReminders(queryable: Queryable, today = new Date()): Promise<ReviewReminderResult> {
  const candidates = await queryable.query<{
    household_id: string;
    recipient_member_id: string;
    review_reminder_frequency: "daily" | "month_end";
    review_count: number;
  }>(reviewReminderCandidatesQuery);
  const dateKey = formatDateKey(today);
  const monthEndWindow = isMonthEndReminderWindow(today);
  let created = 0;

  for (const candidate of candidates.rows) {
    if (candidate.review_reminder_frequency === "month_end" && !monthEndWindow) continue;
    const notification = await enqueueNotification(queryable, {
      householdId: candidate.household_id,
      recipientMemberId: candidate.recipient_member_id,
      type: "review_reminder",
      title: "要確認の支出があります",
      body: `未解決の支出が${candidate.review_count}件あります。`,
      dedupeKey: `review:${dateKey}`,
    });
    if (notification) created += 1;
  }

  return { candidates: candidates.rows.length, created };
}
```
